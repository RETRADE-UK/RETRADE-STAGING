# Monitor inbox — UX research and implementation, 5 October 2026

Baseline: staging main `8f57757`. Existing purchases, PDF, recovery and accounting
changes are retained. This is staging-only; the live repository is untouched.

## Research decisions

| Evidence reviewed | Application here |
| --- | --- |
| [Linear Inbox](https://linear.app/docs/inbox) separates attention/triage from notification-channel settings and supports read/unread and search | Finds leads the workspace; Monitors and Alerts have separate, visible navigation. Unread is an explicit filter, not a claim that every historical item is new. |
| [eBay saved searches](https://www.ebay.co.uk/help/buying/search-tips/saved-searches?id=4051), [notifications](https://www.ebay.co.uk/help/default/default/notifications?id=4203), and [Watchlist](https://www.ebay.com/help/Buying/Finding_Items_Managing_Purchases/Your_Watch_List?id=4046) distinguish searches, item shortlists, and delivery preferences | Monitor rules, RETRADE saves and device/per-monitor opt-in are separate concepts. Save is not a Vinted favourite or a reservation. |
| [NN/g progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) prioritises frequent tasks and reveals secondary complexity on demand | Price, title, photo, condition, seller evidence and warnings remain visible. Description/photos expand. Diagnostics, examples and timing comparison no longer dominate the page. |
| [Slack notification settings](https://slack.com/help/articles/201355156-Configure-your-Slack-notifications) and [channel controls](https://slack.com/help/articles/360056534254-Manage-notifications-for-specific-channels-and-direct-messages) distinguish delivery channels and conversation choices | Device permission alone does not enable every monitor. Both stages have explicit status and controls. |
| [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) addresses small and crowded controls | Primary controls use at least 44 CSS-pixel height, with wrapping and keyboard focus. This design target exceeds the 24px WCAG minimum; it is not an accessibility certification. |
| [WebKit iOS web push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) requires a Home Screen web app and direct user interaction for permission | Permission remains user-triggered. Setup gives Home Screen and blocked-permission guidance; device registration is checked against the signed-in account. Provider acceptance is not claimed as phone receipt. |
| [MDN notification click](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event) documents notification navigation | Item alerts open the exact Vinted UK item using a validated numeric ID, never an arbitrary payload URL. Test alerts reopen the app. |

These are design judgments adapted to RETRADE, not claims of comparative usability
testing or a pixel-copy of another app. The supplied Discord screenshots inform
the information hierarchy; they do not prove authenticated Buy/Offer/Favourite
capabilities or what the approximate total includes.

## Functional audit and change

- Previous layout put all recipe buttons and phone setup before results on mobile.
  Finds now comes first in DOM and visual order; setup lives in dedicated sections.
- Previous feed exposed only the current recipe revision and latest 200 rows.
  History now deduplicates listing identity across all retained rule versions,
  keeps the earliest discovery timestamp, and pages 50 at a time using a timestamp
  and identity cursor. Newest qualifying evidence supplies the displayed details.
- History, unread and saved filters and literal title/ID search run server-side.
  No listing data is cached across accounts in local storage. Older-page browsing
  is not reset by polling; explicit Refresh returns to the newest page.
- Read/save disposition is durable per monitor/listing, independent of revision.
  Writes require verified account ownership and existing matching evidence, and
  the UI waits for confirmation. A RETRADE save never performs a marketplace write.
- Disposition table has owner-read RLS; browser writes and RPC execution are denied.
  The two new RPCs are security-invoker, service-role-only, with fixed search paths
  and explicit ownership checks. No existing evidence is deleted or rewritten.
- Device status checks the exact browser endpoint against the authenticated owner;
  account-wide device count is no longer presented as this device's readiness.
- Source access, monitor enablement, per-monitor notification choice and device
  permission remain independent. Source status stays visible even when diagnostics
  are collapsed. A refusal is not represented as a successful empty scan.

## Remaining activation gates

Read-only staging inspection on 5 October: source blocked, one recipe, zero enabled
recipes, zero captured matches. Last operator check (29 September label) returned
HTTP 403. No repeat challenge/proxy/cookie workaround was attempted. The official
[Vinted Pro docs](https://pro-docs.svc.vinted.com/) do not establish a general buyer
search feed; an authorised source connection still needs a user/provider choice.

No Discord account was connected or messages scraped. A provider feed or a
server-authorised integration requires access details and permission. No source
gate is cleared by this release. No fictional cards enter history or the outbox.

Physical iPhone delivery, live payload enrichment/coverage and multi-day Discord
latency remain unverified. Buy/Offer/Vinted Favourite, calibrated valuations,
automatic Discord ingestion and purchased-to-stock remain unimplemented.

The history query deduplicates retained evidence within one owned monitor before
pagination. Its identity index supports that work, but it is not constant-time for
arbitrarily large histories; load testing/retention policy remains necessary before
large-scale operation. Polling is read-only and stops on hidden pages or disposal.

## Verification and rollback

Synthetic tests cover cursor traversal beyond 200 entries, cross-revision identity,
literal search, saved/read independence, owner isolation, privileged execution,
malformed API input, safe push destinations, failed UI writes, disclosure state,
mobile/desktop geometry and existing monitor recovery contracts. Shared check,
build and full browser suite are release gates; deployment outcome is recorded in
the PR. No real phone recipient is contacted by these tests.

Deploy the additive migration, then the backwards-compatible handler, then UI.
Rollback UI with a fresh cache build; old handler/UI remain compatible. Preserve
the disposition table and detection evidence. Keep source blocked until an
authorised connection is tested. Production promotion requires separate approval.

Staging backend deployment: migration `monitor_history_inbox` applied; handler
version 6 active. Actual database verification confirms both RPCs are invoker-mode,
browser EXECUTE denied, worker EXECUTE allowed, and existing history empty. The
security advisor adds one [anonymous-access notice](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0012_auth_allow_anonymous_sign_ins)
for the new owner-read table, matching staging's existing anonymous test-account
model. It permits only that anonymous account's own rows, not public or other-user
access; writes remain service-only. No other advisor finding changed.
